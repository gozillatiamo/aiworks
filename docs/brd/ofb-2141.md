# OFB-2141 BRD: Paotung Customizable Category Preview Widget

**Ticket:** OFB-2141  
**Phase:** Design & Planning  
**Date:** 2026-06-15  
**Owner:** Product & Platform Team  
**Status:** In Planning  

---

## 1. Executive Summary

Convert Paotung skin's **fixed** category-game-preview component on landing/home pages into a **default-on, backoffice-customizable widget**. Game agencies on Paotung-skin sites edit widget title + rich-text description (w/ SEO hyperlinks) without dev intervention; underlying category game preview preserved. Production-safe: default config = today's render -> zero visible change day one on all live sites.

**Why now?** Google Dec-2025 E-E-A-T core update penalizes "thin" casino pages (bare game grids). Editable hyperlink-capable copy block is direct SEO ranking lever. Competitive parity: GR8 Tech CMS, SOFTSWISS ship multi-tenant content widgets as standard. OFB is behind; this ticket closes the gap.

## 2. Business Context & Goals

### 2.1 Market Insight

- **Asia-Pacific iGaming market:** ~USD 18.5B (2024), ~12.8% CAGR. Thailand (Paotung home) = fastest-growing mobile market.

- **Competitor landscape:** GR8 (30+/100+ pre-built widgets, drag-drop builder, per-brand theming), SOFTSWISS, PieGaming, GammaStack all ship tenant content-widget libraries as baseline. Content-widget = table-stakes CMS capability.
- **Market claim:** GR8 advertises ~5x faster content launch, ~60% dev dependency reduction via self-service widget editing.

### 2.2 Strategic Intent

- **P0:** Move category game preview from **fixed/hardcoded** component → **DB-backed, per-site, backoffice-managed widget** with default behavior = today's exact render.
- **P0:** Enable agency self-service editing (title + rich description, sanitized hyperlinks) without dev ticket or release cycle.
- **P0:** Production-safe rollout: all existing live Paotung sites seeded w/ default config matching current CategoryLandingSection render. Zero migration surprise.
- **P1:** Establish multi-tenant default-widget + per-site-override pattern (foundation for future widget expansion: FAQ, promotions, testimonials, etc.).

## 3. Scope

### 3.1 In Scope

1. **DB Schema + Migration (agent-db)**
   - `category_preview_block` entry in `page.content JSONB` schema (reuse page(site_revision_id, template_code, template_type, content) table).
   - Migration seeding: ALL live Paotung site_revisions get default category-preview block config matching current CategoryLandingSection (title "Slot Games"/"Casino"/"Sports", description = current SEO_HYPERLINKS env JSON, 3 category slots).
   - Rollback-safe (liquibase additive changeset).

2. **Backend API (agent-webservice / Rust)**
   - Extend `content_block` model/serde with `CategoryPreview { title, description_html }` variant.
   - Reuse `page_dao` CRUD for read/update.
   - **Write path:** Sanitize `description_html` server-side (strip XSS, allow safe `<a href>` w/ rel/target), permission-gate to agency role on Paotung-skin sites only.
   - **Read path:** GET `/sites/template/{type}` returns category-preview block per-host via X-Origin header.

3. **Paotung Frontend Render (paotung-template)**
   - CategoryLandingSection.tsx: consume category-preview block via `customization-widget` submodule (already in stack on lobby/promotion/cashback pages).
   - Deterministic fallback: if block absent/malformed -> render hardcoded CategoryLandingSection (today's behavior).
   - Game preview body (actual category game grid) unchanged; widget wraps it.

4. **Backoffice Editor Stub (backoffice)**
   - Build template editor at `sites/[id]/template/page.tsx` (currently `<h1>Template Page</h1>`).
   - Title field + Slate rich-text description (Slate already dep).
   - Hyperlink anchors (rel/target support).
   - Paotung-skin + role (agency) gated.
   - Draft-save before publish (reuse site_revision ACTIVE|DRAFT semantics).

### 3.2 Out of Scope

- **General page builder.** Not a greenfield visual editor; single widget type only.
- **Other skins.** Paotung-only feature; non-Paotung sites never see editor, never ingest category-preview blocks.
- **Other widget types.** FAQ, testimonials, promos = future tickets.
- **Hardcoded CategoryLandingSection removal.** Fallback render stays (safety valve).
- **Env-var seo-hyperlinks.ts retirement.** Only after parity confirmed (last ticket phase).

## 4. Feature Set & User Value

### Feature 1: Default-On Category Preview Widget

**User Value**
- **Player:** Sees same home/landing category game preview as today. Zero visible change.
- **Agency:** Widget surface (title, description, hyperlinks) available for future edits without waiting for dev/release.
- **Platform:** Per-site widget content in DB = structured tenant data, foundation for analytics/recommendations.

**Priority:** P0  
**Unit Economics**
- **Cost lever:** Hardcoded-string + env-JSON edits currently require dev time + release cycle. This move -> future edits = 0 release cost per change.
- **Value lever:** Editable copy block w/ hyperlinks = direct SEO ranking surface. Hyperlink-capable description counters Google E-E-A-T thin-content demotion -> organic traffic -> lower CAC.

**Acceptance Criteria**
- Every existing live Paotung site renders widget byte-identical to current CategoryLandingSection (title, description, hyperlinks, per-category game preview body).
- Driven by seeded default config (DB).
- Safe fallback: if config absent/malformed, deterministically render hardcoded CategoryLandingSection.
- Game preview body behavior unchanged (same game grid, same category slots).

---

### Feature 2: DB-Backed Per-Site Widget Config + API

**User Value**
- **Indirect to player:** Platform content source moves from hardcoded + env-JSON to DB config per-host.
- **Direct to ops:** Content/SEO changes cease to require dev/release.

**Priority:** P0  
**Unit Economics**
- **Cost lever:** Release cycle cost (eng + QA + ops) removed from every content edit.
- **Data moat lever:** Structured per-site content config in DB = foundation for multi-tenant platform intelligence (usage analytics, A/B tests, recommendations).

**Acceptance Criteria**
- Config model extends agent-webservice `content_block` schema (CategoryPreview variant).
- Read API (GET `/sites/template/LANDING` or similar) resolves widget config per-host via X-Origin header.
- Migration seeds default config for ALL current live Paotung sites = byte-identical to current CategoryLandingSection render.
- Rollback-safe: migration is additive (liquibase changeset); absent/malformed config -> deterministic fallback, never blank or crash.
- No dev/release required to edit content after ship.

---

### Feature 3: Backoffice Widget Editor (Title + Rich-Text Description)

**User Value**
- **Agency:** Self-edit widget title + description in backoffice. Draft-save before publish. No dev ticket, no waiting for release.
- **Retention:** Faster SEO iteration, lower vendor lock-in friction vs competitors (GR8/SOFTSWISS).

**Priority:** P1  
**Unit Economics**
- **Value lever:** Agency self-service = support/dev tickets per content change -> 0. Competitive parity defense.
- **Operational:** Removes backlog overhead of "change category description" tickets.

**Acceptance Criteria**
- Backoffice template editor (sites/[id]/template/page.tsx) exposes title + Slate rich-text description fields.
- Scoped to Paotung-skin sites only; non-Paotung sites never see the editor UI.
- Save as draft; publish flow (reuse site_revision ACTIVE|DRAFT toggle).
- Role/permission gated (agency users only; admin role can override all sites).
- Change reflects in paotung-template render per-host within 1-2 request cycles (TTL on site-service cache or immediate invalidate).

---

### Feature 4: SEO Hyperlink Support + Sanitization

**User Value**
- **Player:** Trustworthy content (no XSS), improved search ranking via editorial links.
- **Agency:** Insert internal/external SEO anchors (rel, target controlled). Counters Google E-E-A-T thin-content demotion.
- **Platform:** No XSS/injection breach risk on live prod.

**Priority:** P1  
**Unit Economics**
- **Value lever:** Hyperlink-capable copy = direct SEO ranking lever. Editable anchors = lower reliance on paid acquisition (lower CAC).
- **Risk lever:** Sanitization on write/render = blocks XSS/breach on live prod -> avoids brand damage, regulatory fines, incident response cost.

**Acceptance Criteria**
- Backend (agent-webservice) sanitizes `description_html` on write: strip all HTML except safe `<a>` w/ `href`, `rel`, `target`, `aria-label`.
- Slate editor enforces hyperlink anchors only (no raw `<script>`, `<iframe>`, etc.).
- Render path (paotung-template customization-widget) HTML-escapes all non-hyperlink text; uses `dangerouslySetInnerHTML` only after sanitization confirm.
- OWASP sanitizer (e.g., DOMPurify on client, bleach/ammonia on server) applied at both write and render.
- XSS/injection test in E2E suite (paotung-template E2E or backoffice-cypress).

## 5. Technical Feasibility & Approach

### 5.1 Verdict

**FEASIBLE** — High reuse, low novelty. NOT greenfield: per-site widget infra already exists end-to-end. This ticket = add ONE new widget type (CategoryPreview) + build backoffice editor stub.

### 5.2 Existing Infra to Extend (Do Not Rebuild)

| Repo | Existing Pattern | Reuse Here |
|------|------------------|-----------|
| **agent-db** | `page(site_revision_id, template_code, template_type, content JSONB)`, `site_revision(status ACTIVE\|DRAFT)`, `template_type` enum (LANDING, LOBBY, etc.), content seeded as `[]` block arrays. | Add `category_preview` block schema to content JSONB; migration seeds for all live Paotung sites. Rollback-safe (liquibase). |
| **agent-webservice** | `page_dao` CRUD, GET `/sites/template/{type}` & `/sites/draft/*` resolve content per-host via X-Origin. Role/permission check on write. | Extend content-block schema w/ CategoryPreview variant; reuse page_dao update; sanitize hyperlink HTML on write; permission-gate to agency role. |
| **paotung-template** | `customization-widget` submodule on lobby/promotion/cashback pages. CategoryLandingSection.tsx is hardcoded Thai strings + SEO_HYPERLINKS env JSON (src/features/game/utils/seo-hyperlinks.ts). | CategoryLandingSection → consume category-preview block via customization-widget renderer; fallback to hardcoded if block absent/malformed. Game preview body unchanged. |
| **backoffice** | `sites/[id]/template/page.tsx` is stub (`<h1>Template Page</h1>`). Slate already a dep (used elsewhere for rich text). | Build template editor here: title field + Slate rich-text + hyperlink anchors. Paotung-skin + role gate. Draft-save via site_revision API. |

### 5.3 Build Plan (Dependency Waves)

**Wave 1: Backend (agent-db + agent-webservice)**
1. **agent-db migration:**
   - Add `category_preview` block variant to `page.content` JSONB schema.
   - Seed default config for ALL current `live` Paotung `site_revision` rows: byte-identical to current CategoryLandingSection render (title "Slot Games"/"Casino"/"Sports", description = current SEO_HYPERLINKS env JSON with 3 category hyperlinks).
   - Rollback-safe (liquibase additive changeset).

2. **agent-webservice:**
   - Extend `content_block` model/serde: add `CategoryPreview { title: String, description_html: String }` variant.
   - Reuse `page_dao::update_page()` for write endpoint.
   - Sanitize `description_html` on write: OWASP bleach/ammonia (Rust crate) -> strip XSS, allow safe `<a href rel target aria-label>`.
   - Extend GET `/sites/template/{type}` to return category-preview block.
   - Permission: write-gate to agency role for Paotung skin only (guard w/ `X-Origin` header + role check).

**Wave 2: Frontend Render (paotung-template)**
1. **CategoryLandingSection.tsx:**
   - Fetch category-preview config via site-service (per-host, proxy.ts already does X-Origin forwarding).
   - If block present + valid -> render title + description_html via customization-widget renderer (safe HTML from sanitized backend).
   - If block absent/malformed -> fallback to hardcoded CategoryLandingSection (today's behavior).
   - Game preview body (category game grid) unchanged.

**Wave 3: Backoffice Editor (backoffice)**
1. **sites/[id]/template/page.tsx:**
   - Build editor UI: title input + Slate rich-text editor.
   - Hyperlink support: anchor toolbar (Slate plugin), sets rel/target attrs.
   - Paotung-skin scoping: conditional render (check site.template_type enum or skin code).
   - Role gate: check user role = agency (admin can edit all sites).
   - Save flow: POST to agent-webservice write endpoint w/ site_id + block config; reuse site_revision draft/publish toggle.

**Wave 4: QA + Validation (Cross-repo test suite)**
- **paotung-template E2E:** Widget renders byte-identical on day one; fallback works if config absent; game preview body behavior unchanged.
- **backoffice-cypress:** Agency user can edit title + description, draft-save, publish; non-Paotung sites don't see editor; role-gate enforced.
- **agent-webservice integration tests:** Sanitization strips XSS (e.g., `<img onerror>` -> plain text); safe hyperlinks preserved; rollback scenario (absent config).

### 5.4 Risks & Mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| **Hardcoded CategoryLandingSection fallback not triggered in prod.** Players see broken/blank widget. | P0 | Fallback render tested in E2E (paotung-template); config-absent scenario in integration tests (agent-webservice). Deploy fallback first (paotung-template render), then config in agent-webservice. |
| **Sanitization incomplete; XSS slips through.** Breach on live prod. | P0 | Use OWASP-standard crate (bleach/ammonia in Rust, DOMPurify on client). XSS test in E2E (e.g., inject `<img onerror>`, assert it's escaped). Security review on write + render path. |
| **Migration doesn't seed all live Paotung sites.** Some sites go live w/ no config -> fallback, but expectations were "same render". | P0 | Pre-migration query: count live Paotung site_revisions, spot-check render against CategoryLandingSection hardcoded values. Post-migration: query count again, assert 1:1 match. Rollback plan: revert liquibase changeset (additive, safe). |
| **Backoffice editor slow to load (agent-webservice + Slate on slow network).** Agency user churn. | P2 | Cache site config in paotung-template + backoffice (TTL 60s). Slate editor lazy-load. Monitor latency in QA. |
| **Site-revision ACTIVE\|DRAFT toggle collision w/ other template edits.** Draft published too early or not at all. | P1 | Establish draft-lock semantics: only one editor (category-preview widget) can edit site_revision draft at a time. Alternative: atomic update (CAS on version timestamp). Document in backoffice editor UX (no concurrent edits banner). |

### 5.5 Cross-Repo Dependencies

```
agent-db (schema + migration)
  ↓
agent-webservice (config model + API + sanitization)
  ↓
paotung-template (render CategoryLandingSection w/ block)
  ↓
backoffice (editor UI)
  ↓
paotung-template E2E + backoffice-cypress (validation)
```

**Critical:** Rollout must preserve backward compat:
1. agent-webservice + agent-db deploy first (new schema, default config seeded).
2. paotung-template deploy next (fallback + block render in place).
3. backoffice deploy last (editor UI live).

Rollback: revert in reverse order (backoffice -> paotung-template -> agent-webservice -> agent-db).

## 7. Open Questions & Decisions

1. **Migration strategy for env-var `seo-hyperlinks.ts`:** When do we retire it? After backoffice editor ships + confirmed adoption, or keep as fallback indefinitely?
   - **Decision:** Keep as fallback indefinitely (safety); document deprecation in code comments.

2. **Hyperlink HTML sanitization library:** Rust crate (bleach, ammonia, v_htmlescape)? Or delegate to client (DOMPurify)?
   - **Decision:** Sanitize on agent-webservice write (backend-driven); DOMPurify on paotung-template render (defense-in-depth). Reduces attack surface on server.

3. **Draft-publish semantics:** Single site_revision per site, ACTIVE|DRAFT toggle (collision risk), or new draft_revision table?
   - **Decision:** Reuse existing site_revision ACTIVE|DRAFT (lowest friction). Document draft-lock in editor UX; add integration test for concurrent-edit scenario.

4. **Hyperlink rel/target constraints:** rel="noopener noreferrer" for all external links? target="_blank"? User choice in editor?
   - **Decision:** rel="noopener noreferrer" for external, rel="internal" for same-site (agent heuristic on write). target="_blank" optional (editor checkbox). Document in backoffice help text.

5. **Non-Paotung site behavior:** Error or graceful no-op if a non-Paotung site requests category-preview config?
   - **Decision:** Graceful no-op. API returns empty block or null; paotung-template fallback does not apply (non-Paotung never calls customization-widget for category preview). Backoffice editor hidden for non-Paotung (conditional render).

## Appendix: Glossary & References

- **category-preview block:** New widget-block type (title + description_html) rendered in CategoryLandingSection, stored in `page.content JSONB`.
- **site_revision:** DB table tracking page template per site w/ ACTIVE|DRAFT status; reused for draft-save semantics.
- **Sanitization:** OWASP-standard HTML stripping (bleach on backend, DOMPurify on frontend); XSS-safe hyperlinks (href, rel, target, aria-label only).
- **Fallback render:** Hardcoded CategoryLandingSection (legacy behavior) triggered when category-preview block absent/malformed.
- **E-E-A-T:** Google's Expertise, Experience, Authority, Trustworthiness ranking signal; penalizes thin YMYL content.
- **Multi-tenant default-widget pattern:** One default config deployed to all sites; per-site override in backoffice (foundation for future widget expansion).
