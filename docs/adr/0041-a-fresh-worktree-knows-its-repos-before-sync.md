# A fresh worktree knows its repos before sync, and its session knows when setup is running

**Status:** Accepted.

## Context

Superset gives every ticket its own git worktree and runs `.superset/setup.sh` in it. Setup clones
and onboards every product repo (`aiworks sync`), which takes minutes — but the agent session in
the new worktree starts immediately. Without a guard the agent reads a half-cloned tree, concludes
a repo "does not exist", and wanders.

The first version of the guard, `.claude/hooks/repo-health-check.sh`, lived in one organisation's
workspace and derived the expected repo set from `mani.d/*.yaml` alone. That file set is
*generated by* `aiworks sync` and git-ignored, so in the exact window the hook exists for — before
the first sync — it saw zero expected repos and reported a fresh worktree as ready. It also told
"setup running" from "setup never ran" by `pgrep`, which cannot distinguish a crashed setup from
one that finished, and the hook's header named that organisation's repos.

Setup itself had three gaps the same organisation had patched locally: adapter credentials
(`scripts/{tracker,notify,vcs}/.env`) were provisioned *after* sync, so an adapter call during
onboarding ran without them; there was no place for organisation-only setup such as local host
aliases for a multi-tenant app; and nothing recorded that a setup was in progress.

## Decision

The worktree setup and the readiness check become a default ability of the framework, with no
organisation-specific text in either:

- **Expected repos = `mani.d/*.yaml` ∪ `workspace.config.yaml` `products[].repos[].url`.** The
  committed config is present from the first checkout, so the pre-sync window is covered; the
  generated files are still honoured once they exist.
- **Setup writes a lock the check reads.** `setup_lock_acquire .superset/run/setup.lock` records
  the setup pid at the top level of `setup.sh` and removes it on `EXIT`/`INT`/`TERM`. The check
  classifies the state as `running` (pid alive), `crashed` (lock present, pid gone — hard kill or
  power loss, so the trap never fired) or `idle` (no lock; `pgrep` remains as the legacy fallback).
- **Adapter `.env` files are provisioned in step 2**, before host tooling and sync, honouring
  `SUPERSET_ENV` like the repo `.env` step.
- **An optional `setup_product` hook** in `.superset/products/<product>.sh` runs after the `.env`
  check (step 6b). It is the home for organisation-specific setup. `ensure_hosts_entries` is the
  one shipped helper: idempotent, best-effort, prints the lines to add by hand when root is
  unavailable, never aborts setup.
- **A hermetic selftest** (`scripts/aiworks-superset-selftest.sh`) covers the lock, the three
  states, the union of expected repos, `--status`/`--wait`, the hosts helper and the hook runner,
  under both bash 5 and the macOS `/bin/bash` 3.2.

## Considered options

- *Keep `mani.d/` as the only source.* Rejected: it does not exist when the hook matters most.
- *Commit `mani.d/`.* Rejected: it is generated, and `docs/adr/0004` keeps generated files out of
  the tree.
- *Detect setup by `pgrep` only.* Rejected: cannot separate "crashed" from "finished"; a stale
  clone then reads as ready forever.
- *Run organisation setup inline in `setup.sh`.* Rejected: the framework must stay de-branded;
  the product file is already git-ignored and per-organisation (`docs/adr/0009`).

## Consequences

- A fresh worktree's first session reports `N of M repos ready — setup is running` instead of a
  false green, and `--wait` lets a script block on it.
- A hard-killed setup is reported as *interrupted* with the remedy (re-run `setup.sh`, idempotent).
- `setup_product` is best-effort and must be idempotent; a hook that needs root asks for it or
  prints what to do, it never fails setup.
- `docs/agents/superset.md` is the operator-facing description; this ADR records why.
