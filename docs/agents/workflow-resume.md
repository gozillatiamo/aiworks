# Resuming a workflow after the config changed

**This file is the single source of truth for how a config change reaches a workflow
run.** The short version: it does not. A run carries the config it was born with, and
the only honest way to change that is to start a new one.

## Two snapshots, not one

A workflow script cannot read the filesystem — that is [ADR-0001](../adr/0001-headless-workflow-config-mirror.md).
So `workspace.config.yaml` is mirrored into `.claude/workflows/*.js` as a block of
plain constants, regenerated by `scripts/aiworks config` (and by `aiworks add` /
`remove` / `sync`, which call it for you):

```js
// >>> AIWORKS:CONFIG START — generated from workspace.config.yaml; do not edit by hand <<<
const QUALITY_GATE = 'sonarqube'
```

The workflow **engine** then takes a *second* snapshot: every invocation persists a
copy of the script under the session directory and runs that copy. Resuming with
`{scriptPath, resumeFromRunId}` replays the persisted copy — including its config
block, exactly as it was at the first invocation.

So there are two places a value can be stale, and regenerating the mirror only fixes
the first one. **A run started before a config change never sees that change.**

## The rule

| you changed | do this |
|---|---|
| `workspace.config.yaml` | `scripts/aiworks config`, then invoke the workflow **by name** — a fresh run, a fresh snapshot |
| the workflow's own logic | edit `.claude/workflows/<name>.js`, then invoke **by name** |
| nothing; the run just stopped | resume with `{scriptPath, resumeFromRunId}` — cached agents replay, nothing is re-derived |

A fresh invocation mints a new run id, so the previous run's agent cache is not
reused and the early phases run again. That is the cost, and it is the correct cost:
the alternative is a run whose gates disagree with the config the repo actually has.

A **copy** is the fourth case, and the one that hides. `/dev-cycle` invoked by name runs
`.claude/workflows/dev-cycle.js`; a scratchpad or hand-edited copy runs whatever that file said
when it was copied, and its log is indistinguishable — except for one line. Every dev-cycle run
prints `dev-cycle v<DEVCYCLE_VERSION>` first: compare it with the const at the top of
`.claude/workflows/dev-cycle.js`. If they differ, the run is stale, and no amount of re-running it
picks the change up. Invoke **by name**. (Measured: a stale copy predating the Kickoff skip-gate
re-planned all 8 repos — 1.36M tokens — because the gate it needed did not exist in the copy.)

## Never hand-edit the persisted script

An agent must not edit a persisted run script to change a constant — not to disable a
gate, not to fix a value it believes is stale, not "just this once". Two reasons, and
the second one is the expensive one:

- **A constant in that file is generated output.** Editing it makes the run disagree
  with `workspace.config.yaml` while looking like it agrees. The next person to read
  the config learns the wrong thing about what the run did.
- **It reads as self-modification, and the blast radius is the whole run.** An agent
  rewriting the script it is running cannot be distinguished, from the outside, from
  an agent disabling its own supervision — so the safety layer treats it as the
  latter. In one run this blocked an *unrelated* agent in a later phase, and the repo
  it was working on never opened its MR. The edit was well-intentioned and correctly
  researched; it was still the wrong move, because the cost did not land where the
  decision was made.

If the config genuinely has changed and the cache is worth keeping, a **human** can
refresh the snapshot from the canonical file and resume:

```bash
! cp .claude/workflows/dev-cycle.js <the persisted scriptPath from the run output>
```

That is a copy from the source of truth, not an authored change — and a person chose
it. Both halves matter. An agent proposing it should say so and stop.

## History

**2026-08-10** — a `quality_gate.provider` change landed on the branch mid-run. Resuming
replayed the pre-change snapshot, so the orchestrator edited the constant in the
persisted script. The reasoning was checked (the commit was real, the value was right)
and the outcome was still bad: the safety layer flagged the edit, and the flag blocked
the `open-pr` agent for a different repo two phases later. Fresh invocation would have
cost one re-planning pass. This file exists so the trade is made on purpose.
